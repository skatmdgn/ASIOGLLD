# Batch 18 — original COM apartment, notification listener and Worker teardown

Original: 173056-byte Win64 asioglld.dll, SHA-256 `e2a9088a71e61362b4b1cf9d11717a1278ef26c940e7ca716290cab7a93c5cfd`. RVA addresses below apply only to this original binary. **STATIC reconstruction, not original C++ source or Windows/replica parity. No optimization.**

## New original-to-original call-chain evidence

1. Config initializer `0x6120` calls COM/device setup `0x67E0` at `0x65DB`. That helper zeros ECX and EDX then invokes `ole32!CoInitializeEx(NULL, 0)` at `0x6807` — Windows MTA mode. The next instruction `0x680D` proceeds without inspecting that HRESULT, then `0x682A` invokes `CoCreateInstance`. It **does** check the returned *enumerator pointer* at `0x6830`. Do not conflate untested apartment HRESULT with a successful enumerator allocation.
2. The PE static import directory contains **CoInitializeEx, but no CoUninitialize**. This observation **does not establish** an unbalanced Windows COM apartment because dynamic API binding, caller ownership, thread state and actual results remain unverified. No Windows runtime or memory leak has been observed.
3. Both original notification client instances use the 24-byte listener layout (vtable+0, interlocked refcount+0x08, owner+0x10). Config constructs at `0x683A`, AddRef `0x6871`, Register `0x687D`; Worker constructs around `0x1157`, AddRef `0x1189`, Register `0x1196`. **Neither registration return HRESULT is separately tested** in the immediately following code. The existence of the stored pointer is not a verified successful OS registration. Actual OS-owned COM references are unknown.
4. Teardown calls `UnregisterEndpointNotificationCallback` using stored pointer guards, rather than a separately verified registration-success flag. CAsio destructor calls worker unregister `0x1354` then listener Release `0x1363`, CriticalSection deletion `0x136E`, worker memory free `0x1394`; config unregister at `0x1428` and associated Release calls. Another config cleanup path calls unregister `0x6674`.
5. In the observed `CAsio` destructor code window `0x12C0–0x1475`, there is **NO DIRECT CALL** to WorkerStop `0x94B0`. WorkerStop has its own conditional wake/3000ms wait and cleanup routine. This does **not prove** that destruction executes with a live worker: upstream `disposeBuffers`, indirect calls, exception paths and actual host ordering must be examined. Do not silently merge destructor and WorkerStop in a behavior-fidelity implementation.
6. Original IMMNotificationClient vtables at RVA `0x208C8` / `0x209A8` have all 8 slots verified. Both use QueryInterface `0x5EC0` and AddRef `0x5E80`, but distinct Release `0x5E90` / `0x8EF0` and distinct device-state action `0x5F70` / `0x8F20`.
